## 1. The security defect — a rule file could be a symlink

Found by building a hostile project rather than by reading the code.

```
.kiln/rules/evil.md -> /etc/hostname
| src/** | evil.md |
```

`classify` resolved the rule file with `resolve(rulesDir, file)` and checked
`isInside(rulesDir, path)`. Both are string arithmetic and neither knows what a symlink is,
so the path was judged to be inside `.kiln/rules/`, `existsSync` followed the link and
agreed it was there, and doctor reported:

```
[ ok ] rules routing: 1 rule file(s), 1 route(s), all resolved
```

`kiln rules w1 --stage plan` then printed the file:

```
--- evil.md · routed from src/** ---
HCM-DKP-096
```

That is the machine's hostname. Point the link at `.env`, `~/.aws/credentials` or a private
key and **the rules router is a file-read primitive that hands the contents to the agent**.

### Why it got in

D52 settled this for **writes**: a symlink leaf is rejected, never followed — the
arbitrary-file-overwrite primitive agent-skills #295 rates High. The write path goes through
`resolveTarget`, which refuses a link. The reader was new code and used a plain `resolve`.

The lesson generalises past this one line: **a safety rule that lives inside one helper is
only as wide as that helper's callers.** `resolveTarget` carried D52; anything resolving a
path another way inherited nothing.

Fixed in #117. A rule file that is a symlink, or sits behind a symlinked directory, resolves
to `escapes` and is never read — the directory half matters, because refusing only the leaf
leaves `rules/theirs/x.md` where `theirs` is the link.

## 2. "That is all" — the update path

`user-view.md` §14 read:

> Updating kiln: `/plugin update kiln`. **That is all** — kiln writes nothing there (D39).

Both halves are true and the conclusion is false. Writing nothing into the project is the
point; it is also why a checkout that already had the push floor keeps the hook the **older**
kiln wrote. D105 made that a `stale` finding, reported to whoever runs `kiln doctor`.

Measured on a real monorepo after rc.19: **five checkouts all `stale`**, having run the whole
of rc.18 carrying the submodule bug rc.19 had fixed, while every run printed `Ready.`

The whole of kiln's advice about updating pointed the user at a finished state they had not
reached. Fixed in #118 (D104): `kiln open` reports an unarmed floor once per run, and both
the README and §14 now say `/plugin update kiln`, **then `kiln doctor`**.

and leaving it there after the code had been exercised would misreport a real measurement as
an open risk — which is D7 item 3 pointed at kiln's own documentation.

## 5. The method note

Two of the three findings came from doing something rather than reading something: building a
hostile `.kiln/rules/` and re-running the corpus after an update. The stale statements came
from reading — and they are the least valuable third.

That is the same ratio the 2026-09-20 audit reported, and it is the argument for the read-back
being a **build** step rather than a proofread. A section of prose can only be checked against
another section of prose. A product can be asked.
